## How to read this

- **Categories.** `DRIFT`: copies that already disagree. `DUP`: copies that still agree. `BYPASS`: code that reimplements an existing shared helper. `HELPER`: inline logic that should be a named utility. `COMPONENT`: a repeated JSX or hook pattern that should be one shared component or hook.
- **VERIFIED** means the cited lines were read and the claim confirmed independently of the agent that raised it. **REPORTED** means an agent raised it with citations and it is plausible, but it was not re-read. Where two or more agents raised the same finding independently, that is noted.
- Line numbers are from 366c059. If one does not match, search for the quoted expression.

## DRIFT

### D1. The aero chart ends forward flight at an ejection charge (HIGH, VERIFIED, raised by two agents)

- `components/canvas/FlightChart.tsx:117-126` `clipT`: `at('RECOVERY_DEVICE_DEPLOYMENT') ?? at('EJECTION_CHARGE') ?? at('APOGEE') ?? summary.timeToApogee ?? maxT`.
- `services/flight/flightEvents.ts:190-199` `forwardFlightEnd`: deployment, else apogee, else the summary. Its doc comment says an ejection charge is not an end, because the kernel records a booster's charge in the sustainer branch at booster burnout. `SimSummary.tsx:230` and `csvExport.ts:406` already use it for Max q·α.

**Drift.** With no deployment event (a staged sustainer with no recovery, or a charge with no device), the chart's CP, stability and q·α series stop at the charge, which can be booster burnout, while the Max q·α tile beside it measures up to apogee. The chart's own comment says "recovery deploy, else apogee". `forwardFlightEnd` is right; it is documented and tested.

**Also (REPORTED, one agent).** `components/canvas/flightScene.ts:118` `dpT = evT('RECOVERY_DEVICE_DEPLOYMENT') ?? evT('EJECTION_CHARGE') ?? apT` and `:144` use the same fallback for when the 3D model turns nose-up and shows the chute. The other agent treats that as a different question. Decide whether the 3D view should also skip a booster's charge.

**Fix.** `Math.min(forwardFlightEnd(flight.result), maxT)`. About 8 lines.

### D2. Scaling a part leaves automatic radii stale (HIGH, VERIFIED)

- `state/store.ts:1119` `commitTree(syncAutoShoulders(scalePart(...)))` and `:1127` `commitTree(syncAutoShoulders(scaleRocket(...)))`.
- `services/design/treeEdit.ts:43` `syncDerived = (tree) => syncAutoShoulders(syncAutoRadii(tree))`, which every other tree edit ends with (`treeEdit`, `componentActions.replaceInPlace`, `clipboard`).

**Drift.** The scale actions skip `syncAutoRadii`. The comment at `store.ts:1122-1125` says every radius scales by the same factor, which holds only for a whole-rocket scale with offsets on. Scaling one body tube 2x leaves its neighbors' `foreRadiusAuto`, `outerRadiusAuto` and ring `innerRadiusAuto` at their old stored values. The drawings, the report and the printable solids read the stored values while the kernel flies the resolved ones, until an unrelated edit runs `syncDerived`. `componentActions.scaleComponent` (Scale fin) goes through `replaceInPlace` and is right.

**Fix.** `syncDerived(scalePart(...))` and `syncDerived(scaleRocket(...))`. About 4 lines. Scale goldens may need the resolved radii.

### D3. Two validators of a motor curve the kernel accepts (HIGH, VERIFIED)

- `services/motors/motorCurve.ts:19-25` `hasUsableCurve`: finite arrays, at least `MIN_CURVE_SAMPLES`, equal lengths.
- `engine/openRocketEngine.ts` `assertFiniteCurve` (called from `setMotorById`): also refuses a non-finite or non-positive diameter or length, times running backwards, negative masses and all-zero masses.

**Drift.** `buildRocket.ts:59` seats any motor `hasUsableCurve` accepts. The motor parsers do not refuse backwards times or zero masses, so an imported `.eng` or `.rse` with either passes the app's check and then throws inside `setMotorById`, which fails the whole design build (error banner) where `runnability.hasThrustCurve` should have marked the run "no usable motor". The same check feeds `flightConfigs.primaryMotor`, `loadOrk` and `thrustcurve`. The engine's rule is the complete one.

**Fix.** `curveProblem(m): Keyed | null` in `motorCurve.ts` holding every check; `assertFiniteCurve` throws from it; `hasUsableCurve = (m) => !!m && curveProblem(m) === null`. About 40 lines. `motorCurve` must not import the engine.

### D4. Tube bore read without `tubeRadii` (HIGH, VERIFIED; leftover of old D30)

- `services/parts/componentFit.ts:35-43` `innerDiameter`: `(or - th) * 2`, undefined when the wall is 0 or at least the radius.
- `services/motors/motorPicker.ts:52-65` `mountFit`: `bore: (or - th) * 2 * 1000`.
- Shared reader: `services/design/discGeometry.ts:50-59` `tubeRadii`, which the 2D and aft views use. `components/canvas/rocketPieces.ts:483` and `:625` also inline it (agreeing).

**Drift.** A filled body tube has `innerR: 0` in `tubeRadii` (`BodyTube.getInnerRadius`); the other two give the full bore, so the motor picker's "fits the mount" and the part picker's coupler ranking treat a solid tube as hollow. A zero or oversized wall gives `max(0, or - th)`, undefined, or a negative bore depending on the copy. A missing `outerRadius` uses the kernel default in `tubeRadii` and null in the others. `tubeRadii` matches the kernel.

**Fix.** `tubeRadii(node)?.innerR` at all four sites. About 10 lines.
